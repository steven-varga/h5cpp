5 * on_collector — route a single HDF5 operation through the process-global lock.
6 *
7 * HDF5 (threadsafety OFF) has lock-free global state (H5FL free-lists, H5CX
8 * context), so the C-API must be serialized exactly as HDF5's own threadsafe
9 * build does. Under H5CPP_MULTITHREAD on_collector takes the process-global
10 * recursive HDF5 mutex (h5::impl::capi_lock, defined in H5Iall.hpp) around the
11 * op; in a classic build capi_lock is a no-op, so on_collector is a zero-overhead
12 * pass-through.
13 */

20// Run `op` as a single mutually-exclusive HDF5 operation. Under H5CPP_MULTITHREAD
21// this takes the process-global HDF5 lock (h5::impl::capi_lock, defined in
22// H5Iall.hpp) for the whole op — HDF5 Threadsafety-OFF has lock-free global state
23// (H5FL/H5CX), so the C-API must be serialized exactly as HDF5's own threadsafe
24// build does. Any thread may run the op; only one is inside HDF5 at a time, and
25// nested h5cpp calls re-enter the lock for free (thread-local depth). In a classic
26// build capi_lock is a no-op, so this is a zero-overhead pass-through.
27//
28// (An earlier design routed HDF5 through a dedicated collector THREAD; that model
29// is retired. A single thread can't own ALL HDF5 — H5_term_library runs atexit on
30// the main thread and property-list/refcount calls happen on the caller — so the
31// free-lists corrupted across threads. The process-global lock here lets ANY thread
32// run the op while keeping exactly one inside HDF5 at a time.)
33template <class Op>
34inline auto on_collector(Op&& op) -> std::invoke_result_t<Op> {
35 capi_lock _lk; // global HDF5 lock under MT; no-op in classic builds
36 return std::forward<Op>(op)();
37}
38
39} // namespace h5::impl
